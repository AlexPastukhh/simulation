## Нужда и границы (пока кандидат)

**N-CODE-NEXT-01 / user origin:** Shell должен подходить для разных профилей, контекстов и инструментов, не становясь частью симулятора.

**N-CODE-NEXT-02 / user origin:** готовая или минимально подготовленная рабочая ситуация должна открываться как Context, продолжаться/развиваться и комбинироваться с другими Context.

**N-CODE-NEXT-03 / user origin:** механизмы работы в разных областях должны быть переиспользуемы, но узкие инструменты не должны предлагаться в неподходящих ситуациях.

**Candidate invariants (проверить до commit):**
- Никакая экранная операция сама по себе не создаёт и не копирует фактические события/Plan/History.
- Context не обязан быть полной симуляцией или иметь History.
- Окно/экран — отображение ресурсов, не их обязательный владелец; один экран может показывать несколько контекстов.
- Готовые и постепенно собранные композиции используют те же определения инструментов.
- Предметный Scope Mechanism может быть внутри профиля даже для двух его контекстов; межпрофильный — в интеграционной области; общие примитивы — в Shell. Узкие папки нужны при реальной специализации, но проверка применимости должна быть исполняемой.
- Старые локальные данные и `content-v6/layout-v3` не теряются и не переписываются без явного миграционного решения.

### Правила выполнения групп

- **Единица пользовательской приёмки — группа**, а не каждый SRU. Приемлема реализация несколькими внутренними коммитами, но **не обязательны девять отдельных публикаций и приёмок**. Поставлять частичную группу как полностью готовую нельзя. Решение о промежуточной публикации принимается по реальной необходимости и явно отмечает ограничения.
- **Внутри G-CODE-02 обязательная короткая проверка:** `SRU-02` (разделить идентичности/источники) → минимальный Context adapter из `SRU-03` при необходимости → пробный одновременный показ A/B из `SRU-04`. Это **контрольная точка проекта**, а не самостоятельный пользовательский релиз. После неё уточнить оставшуюся реализацию `SRU-03–05`; цель полной группы сохраняется.
- **G-CODE-02 принимается целиком, когда:** (1) Context A и B обладают независимым State по выбранному правилу copy-by-default; (2) два обычных View могут показываться рядом и адресуются корректно; (3) минимальный Context без History работает; (4) единый Context Template разворачивает **комплект четырёх экранов**, а «+ Экран» остаётся generic; (5) старые `content-v6/layout-v3` и пользовательские A/B данные доступны после сохранения и перезапуска; (6) новая документация показывает доказанное поведение.
- **G-CODE-03 принимается целиком, когда:** (1) Comparison использует явные входы/разрешённые эффекты и ничего не меняет в фактических A/B данных; (2) неприменимый механизм отвергается; (3) готовая A+B композиция и поэтапная сборка дают эквивалентный результат; (4) результат/привязки восстанавливаются после перезапуска.
- **G-CODE-04 принимается целиком, когда:** (1) синтетический второй профиль работает через объявленные интерфейсы, без доступа к приватному `DemoStore` другого профиля; (2) негативные проверки совместимости проходят; (3) пройден полный совместный сценарий G-CODE-02/03, миграционные fixture и релевантные автоматические/UI проверки; (4) документация и опубликованный код одной версии.
- **`SRU-CODE-09` — поперечная единица:** проверки State/History, миграций, тестов и точечные изменения документации выполняются **внутри каждой группы** до её приёмки; только общая интеграционная проверка завершается в G-CODE-04. Таким образом, группировка **уменьшает организационные этапы, но не уменьшает обязательные проверки**.
- **Обновление документации:** после проверки каждого реализованного изменения обновлять затронутый раздел у его владельца; **сквозную приёмку и согласованную публикацию кода/документации делать по группе**. Не создавать отдельный файл плана на каждую группу. Исходная матрица `SRU → docs` ниже остаётся источником конкретных владельцев.
- **Открытые решения:** `F-U-CODE-02` (навигационная принадлежность экранов), `F-U-CODE-03` (view-local/shared selections) и явные shared-reference semantics следует разрешить **до соответствующего изменения внутри G-CODE-02**. Они не повод снова делить группу на четыре самостоятельные поставки.

### Почему группы, а не девять отдельных релизов

Отдельная адресация (`SRU-02`) или одна Context-модель (`SRU-03`) ещё не решают пользовательскую задачу. Вместе с `SRU-04–05` они позволяют реально создать Context A/B, открыть два представления и начать работу. Аналогично абстракция Scope без готового и ручного сценариев композиции даёт мало проверяемой ценности. Сохранённая **ранняя проверка адресации** снижает риск дорогого переразработанного runtime, а **совместная приёмка группы** убирает лишние публикации/согласования. Трудозатраты и календарное время групп количественно не измерены; неизвестный срок не превращается в обязательный дедлайн.

## Приёмочные истории (пока candidate)

1. Новый пользователь создаёт рабочий Context «Планирование приложения» с минимальными требованиями без History, затем добавляет новые ресурсы и продолжает после перезапуска.
2. Пользователь открывает готовую Architecture A+B композицию: оба контекста существуют независимо, четыре полезных экрана и Comparison настроены.
3. Пользователь начинает с A, потом добавляет B и подключает Comparison: исходные ресурсы и результат используют тот же контракт, что и готовая композиция.
4. На одном экране одновременно отображаются две обычные Architecture views для A и B, а не специальный жёстко запрограммированный обход `allData.A/B`.
5. Профильный инструмент не предлагается неподходящим контекстам; межпрофильное соединение требует совместимого контракта/адаптера.

## Scope Mechanisms: состав и размещение (кандидат для будущего кода)

- Определение механизма и его **настроенный экземпляр в Workspace** — разные сущности. Механизм описывает возможности/предметную операцию; экземпляр хранит реальные входные ресурсные ссылки, параметры и область результата.
- **Четыре аспекта области:** доступность/разрешения; участники и входы; разрешённые изменения/выходы; экран/окно представления. Scope — не просто UI-контейнер и не иерархия Screen→Window.
- Механизмы одного профиля (в том числе сравнение двух его контекстов) предполагаются под `profiles/<profile>/scope-mechanisms/`; предметно-независимые — в Shell; межпрофильные — в `integrations/scope-mechanisms/`. Специализированные механизмы можно группировать в подпапки по типу/сценарию/контексту **по необходимости**, без пустых каталогов.
- **Папка не обеспечивает запрет использования:** runtime проверяет доступность и семантическую совместимость. Одинаковая JSON Schema ещё не гарантирует совместимость данных. Начать с одного конкретного read-only механизма и отрицательного теста.
