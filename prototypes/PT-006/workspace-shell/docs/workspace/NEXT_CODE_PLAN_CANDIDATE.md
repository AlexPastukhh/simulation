## Нужда и границы (пока кандидат)

**N-CODE-NEXT-01 / user origin:** Shell должен подходить для разных профилей, контекстов и инструментов, не становясь частью симулятора.

**N-CODE-NEXT-02 / user origin:** готовая или минимально подготовленная рабочая ситуация должна открываться как Context, продолжаться/развиваться и комбинироваться с другими Context.

**N-CODE-NEXT-03 / user origin:** механизмы работы в разных областях должны быть переиспользуемы, но узкие инструменты не должны предлагаться в неподходящих ситуациях.

**Candidate invariants (проверить до commit):**
- Никакая экранная операция сама по себе не создаёт и не копирует фактические события/Plan/History.
- Context не обязан быть полной симуляцией или иметь History.
- Окно/экран — отображение ресурсов, не их обязательный владелец; один экран может показывать несколько контекстов.
- Готовые и постепенно собранные композиции используют те же определения инструментов.
- Предметный Scope Mechanism может быть внутри профиля даже для двух его контекстов; межпрофильный — в интеграционной области; общие примитивы — в Shell. Узкие папки нужны при реальной специализации, но проверка применимости должна быть исполняемой.
- Старые локальные данные и `content-v6/layout-v3` не теряются и не переписываются без явного миграционного решения.

## Candidate SRU — последовательность для уточнения, не задачи к немедленному исполнению

| SRU | Цель / ограниченная проверка | Предпосылка | Выход и критерий |
|---|---|---|---|
| **SRU-CODE-01** | Аудит существующих локальных экранных правок и опубликованной версии; сохранение/версионирование | Копии текущих веток и тестов | Согласован объём интеграции `duplicateScreen`/`addScreensFromTemplates`, без потери старых данных/изменений |
| **SRU-CODE-02** | Контракт адресации: профиль/контекст/ресурс/вид/вкладка как разные ID | SRU-01; правила data ownership | Два независимых источника Architecture A/B могут адресоваться без глобального переключения всей раскладки |
| **SRU-CODE-03** | Минимальный runtime Context с созданием из шаблона и подготовленного State | SRU-02; copy/ref semantics | Создать два Context из одного определения без смешения State; минимальный Context без History корректно работает |
| **SRU-CODE-04** | Многоисточниковые View bindings и раздельное состояние представлений | SRU-02/03 | Показать обычные окна Architecture A и B одновременно на одном экране; исторические и плановые выборы не путаются |
| **SRU-CODE-05** | Один Context Template «Эволюция архитектуры» с набором 4 экранов | SRU-03/04; использовать существующий layout engine | «+ Контекст» создаёт рабочий контекст и предложенные экраны; «+ Экран» не публикует четыре отдельных предметных шаблона |
| **SRU-CODE-06** | Минимальный Scope Mechanism: область, bindings, applicability, effects, presentation | SRU-02/04 | Comparison(A,B) получает явные источники и read-only результат; одинаков для готового и ручного пути |
| **SRU-CODE-07** | Готовая многоконтекстная композиция и последующая ручная сборка | SRU-03/05/06 | Один результат достигается двумя путями: сразу открыть A+B или добавить B и настроить Comparison позже |
| **SRU-CODE-08** | Минимальная межпрофильная проверка + узкие правила применимости | SRU-06 | Synthetic second-provider link без импорта внутренних хранилищ другого профиля; несовместимый Scope не исполняется |
| **SRU-CODE-09** | Legacy persistence, migration, tests/UX/docs | По мере каждого предшествующего SRU | Сохранены A/B content/history/layout и пользовательские данные; smoke/Unit/build/lint; docs CURRENT обновлены по факту |

**Версия минимальной проверки:** SRU-01 → SRU-02 → SRU-04 на существующих A/B, если это возможно без преждевременного полного registry; после такой проверки пересмотреть необходимость и порядок остальных SRU. Это **Proposal**, а не автоматическая смена обещанного результата.

## Открытые решения перед реализацией

- **F-U-CODE-01 / UPSTREAM:** Scope Mechanism — один исполняемый framework или минимальные контракты поверх существующих Shell primitives? Начать с 1–2 реальных взаимодействий, чтобы не создать тяжёлый движок без доказанной пользы.
- **F-U-CODE-02 / UPSTREAM:** должны ли экраны иметь навигационную принадлежность Context или быть полностью Workspace-global? Предпочтение — Workspace-owned с metadata группы происхождения, а не жёсткое вложение.
- **F-U-CODE-03 / UPSTREAM:** какие поля `events.selectedId`, `plan.selectedStepId`, `comparison.focus` общие внутри контекста, а какие локальные для вкладки?
- **F-U-CODE-04 / UPSTREAM:** загружать prepared context как рабочую копию или ссылку; кто владеет shared resources и права на изменение?
- **F-U-CODE-05 / CURRENT:** когда и как интегрировать существующие незакоммиченные 4-screen изменения и нужны ли промежуточные compatibility aliases для сохранённых layouts?

Это вопросы для **следующего pre-work**. Не повышать их до Fundamental Requirement и не считать proposed directory names runtime contracts.

## Приёмочные истории (пока candidate)

1. Новый пользователь создаёт рабочий Context «Планирование приложения» с минимальными требованиями без History, затем добавляет новые ресурсы и продолжает после перезапуска.
2. Пользователь открывает готовую Architecture A+B композицию: оба контекста существуют независимо, четыре полезных экрана и Comparison настроены.
3. Пользователь начинает с A, потом добавляет B и подключает Comparison: исходные ресурсы и результат используют тот же контракт, что и готовая композиция.
4. На одном экране одновременно отображаются две обычные Architecture views для A и B, а не специальный жёстко запрограммированный обход `allData.A/B`.
5. Профильный инструмент не предлагается неподходящим контекстам; межпрофильное соединение требует совместимого контракта/адаптера.
