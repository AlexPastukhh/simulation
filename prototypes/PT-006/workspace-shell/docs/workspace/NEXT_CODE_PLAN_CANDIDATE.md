## Нужда и границы (пока кандидат)

**N-CODE-NEXT-01 / user origin:** Shell должен подходить для разных профилей, контекстов и инструментов, не становясь частью симулятора.

**N-CODE-NEXT-02 / user origin:** готовая или минимально подготовленная рабочая ситуация должна открываться как Context, продолжаться/развиваться и комбинироваться с другими Context.

**N-CODE-NEXT-03 / user origin:** механизмы работы в разных областях должны быть переиспользуемы, но узкие инструменты не должны предлагаться в неподходящих ситуациях.

**Candidate invariants (проверить до commit):**
- Никакая экранная операция сама по себе не создаёт и не копирует фактические события/Plan/History.
- Context не обязан быть полной симуляцией или иметь History.
- Окно/экран — отображение ресурсов, не их обязательный владелец; один экран может показывать несколько контекстов.
- Готовые и постепенно собранные композиции используют те же определения инструментов.
- Предметный Scope Mechanism может быть внутри профиля даже для двух его контекстов; межпрофильный — в интеграционной области; общие примитивы — в Shell. Узкие папки нужны при реальной специализации, но проверка применимости должна быть исполняемой.
- Старые локальные данные и `content-v6/layout-v3` не теряются и не переписываются без явного миграционного решения.

## Открытые решения перед реализацией

- **F-U-CODE-01 / UPSTREAM, вариант выбран 2026-10-11:** пользователь выбрал **минимальные контракты Scope Mechanism** поверх проверенных Shell primitives вместо полноценного движка сразу; остаётся открыть конкретный API и границы первой реализации (read-only A/B Comparison).

- **F-U-CODE-03 / UPSTREAM:** какие поля `events.selectedId`, `plan.selectedStepId`, `comparison.focus` общие внутри контекста, а какие локальные для вкладки?
- **F-U-CODE-04 / UPSTREAM, default выбран 2026-10-11:** новый Context получает **независимую рабочую копию State по умолчанию**; shared references только явно. Открыты provenance, owner и разрешения на изменение явно связанных ресурсов.
- **F-U-CODE-05 / CURRENT:** когда и как интегрировать существующие незакоммиченные 4-screen изменения и нужны ли промежуточные compatibility aliases для сохранённых layouts?

## Приёмочные истории (пока candidate)

1. Новый пользователь создаёт рабочий Context «Планирование приложения» с минимальными требованиями без History, затем добавляет новые ресурсы и продолжает после перезапуска.
2. Пользователь открывает готовую Architecture A+B композицию: оба контекста существуют независимо, четыре полезных экрана и Comparison настроены.
3. Пользователь начинает с A, потом добавляет B и подключает Comparison: исходные ресурсы и результат используют тот же контракт, что и готовая композиция.
4. На одном экране одновременно отображаются две обычные Architecture views для A и B, а не специальный жёстко запрограммированный обход `allData.A/B`.
5. Профильный инструмент не предлагается неподходящим контекстам; межпрофильное соединение требует совместимого контракта/адаптера.

## Scope Mechanisms: состав и размещение (кандидат для будущего кода)

- Определение механизма и его **настроенный экземпляр в Workspace** — разные сущности. Механизм описывает возможности/предметную операцию; экземпляр хранит реальные входные ресурсные ссылки, параметры и область результата.
- **Четыре аспекта области:** доступность/разрешения; участники и входы; разрешённые изменения/выходы; экран/окно представления. Scope — не просто UI-контейнер и не иерархия Screen→Window.
- Механизмы одного профиля (в том числе сравнение двух его контекстов) предполагаются под `profiles/<profile>/scope-mechanisms/`; предметно-независимые — в Shell; межпрофильные — в `integrations/scope-mechanisms/`. Специализированные механизмы можно группировать в подпапки по типу/сценарию/контексту **по необходимости**, без пустых каталогов.
- **Папка не обеспечивает запрет использования:** runtime проверяет доступность и семантическую совместимость. Одинаковая JSON Schema ещё не гарантирует совместимость данных. Начать с одного конкретного read-only механизма и отрицательного теста.
