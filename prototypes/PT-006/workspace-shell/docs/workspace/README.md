# Workspace — как он работает сейчас

**CURRENT / опубликованный Git `main`; локальные незакоммиченные экранные изменения отличаются (снимок 2026-10-11).** Здесь только фактически реализованное поведение. Целевая архитектура самостоятельных контекстов, ресурсов и Scope Mechanisms — [отдельный кандидат](CANDIDATE_MODEL.md).

## Текущая модель

Тип `Workspace` из [src/shell/workspace.ts](../../src/shell/workspace.ts) — **layout**, не реестр всех предметных данных:

```ts
type Workspace = { version: 3; activeScreenId: string; screens: Screen[] }
type Screen = { id: string; title: string; panels: Panel[] }
type Panel = { id: string; rect: Rect; tabs: string[]; active: string | null }
```

Экран объединяет окна, окно — вкладки с ID зарегистрированных видов. Многократное отображение вида не означает независимых копий его предметного State.

## Что сейчас означают контексты A/B

В [SimulatorProfile.tsx](../../src/profiles/architecture-simulator/SimulatorProfile.tsx) профиль хранит `Branch = 'A' | 'B'`, два независимых набора `DemoStore`, их данные и подготовленную историю. Профиль же реализует кнопки Architecture A/B.

В Shell `WorkspaceProfile.contextId` служит **ключом выбора всей раскладки**: `layouts[profile.contextId]`. A и B имеют раздельные ключи `pt006-simulator-layout-[A|B]-v3`, а профиль хранит доменные данные в `pt006-simulator-content-[A|B]-v6`. Существующие миграции сохраняются; в опубликованном `main` «+ Экран» создаёт пустой экран. Дополнительные действия с копированием и набором экранов подготовлены только локально, для [следующей кодовой итерации](NEXT_CODE_PLAN_CANDIDATE.md). Детали обратной совместимости `v5/v4/v3`, ключей и сохранения пользовательских данных находятся в [датированном журнале исправлений PT-006](../../../PT006_REMEDIATION_2026-10-10.md); здесь они не дублируются.

Сейчас **нет** общего `ContextInstance` или создания третьего произвольного контекста. Нельзя поставить обычные окна Architecture A и Architecture B рядом в одной раскладке Shell. Предметный вид `comparison` обращается к `allData.A/B` прямо из SimulatorProfile — это частное сравнение авторского примера, не универсальный механизм.

## Уровни состояния

- **Layout State** — геометрия, экраны, окна и вкладки Shell.
- **Domain State** — факты, требования, Plan, архитектура и работа в профиле.
- **History** — подготовленные event-linked `HistoryFrame` и `PlanRevision`, не автоматический replay любых пользовательских правок.
- **Selections** — в текущем `DemoStore` хранится и ряд выборов вида (например, событие/Step). Это не означает, что у каждого окна имеется собственный независимый выбор.

Профиль также предоставляет JSON Schema для своих 18 видов. Схема описывает допустимую форму данных и сама по себе не гарантирует предметную совместимость ресурсов.

## Границы текущего прототипа

Один активный профиль; нет универсального жизненного цикла контекстов, каталога ресурсов, общих `ResourceRef` с `contextId`, межпрофильного исполнения, полноценных инструментов Scope или независимых входов одного виджета из разных контекстов. Пользователь работает через [механизмы Shell](../shell/README.md) с предметными данными [профиля симулятора](../profiles/architecture-simulator/README.md).

Новые определения **Context Template**, **Prepared Context**, **Interaction**, **Composition** и **Scope Mechanism** описаны отдельно как [CANDIDATE](CANDIDATE_MODEL.md), а не как существующий API.
