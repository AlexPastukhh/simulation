# Workspace — текущая реализация PT-006

**CURRENT / G-CODE-04, 2026-10-11.** В PT-006 доступны **два режима Architecture Simulator** и отдельный **Markdown Fixture** — все используют тот же Shell: прежние отдельные A/B раскладки и новый **«Общий Workspace»** с несколькими Context. Это не совместное многопрофильное Workspace; реализован **один профильный read-only Scope Mechanism** для Architecture Comparison, не универсальный Scope Engine. [Shell](../shell/README.md) · [план остальных этапов](NEXT_CODE_PLAN_CANDIDATE.md).

## Как пользоваться

**Навигация по экранам:** все вкладки Screen расположены отдельными строками под верхней панелью команд. Полоса занимает всю ширину Workspace и автоматически переносит вкладки, когда их становится много. Горизонтального скроллбара и стрелок у экранов нет; каждый Screen выбирается непосредственно кликом. Прокрутка вкладок **внутри окон** — отдельный механизм и не изменена.

1. В верхней панели нажмите **«⊞ Общий Workspace»**. Первый запуск создаёт **отдельную** общую раскладку из сохранённых A и B раскладок; старые ключи/экраны не удаляются. Кнопка «← Отдельные A/B раскладки» возвращает прежний интерфейс.
2. Выберите экран **A · Архитектура и реализация**, создайте окно **«+ Окно»** и через каталог содержимого добавьте **B · Architecture**. Теперь обычные Architecture A и Architecture B видны одновременно на **одном** Screen. Переходы из B остаются привязанными к B; переходы из A — к A.
3. Нажмите **«+ Контекст»** и выберите **«Эволюция архитектуры»**. Создаётся новый Context с **независимой рабочей копией текущего State A**, его provenance и четырьмя обычными тематическими экранами. Данные A/B от этого не изменяются.
4. Другой вариант **«Минимальный контекст»** создаёт один экран с редактируемыми требованиями/заметками, **без History**. Содержимое сохраняется независимо и доступно после перезапуска.
5. **«+ Экран»** по-прежнему делает пустой экран или копию текущего: это изменение представления, не копирование Context или State.
6. **Готовая композиция:** нажмите **«⇄ Композиция» → «Готовая A+B» → «Открыть A+B + Comparison»**. Создастся новый Screen с Architecture A, Architecture B и отдельным окном Scope Comparison. Источники привязаны явно.
7. **Ручная сборка:** создайте пустой экран, откройте по одному обычные Architecture для двух Context, затем **«⇄ Композиция» → «Ручная сборка»**. Выберите первую и вторую стороны, нажмите **«Связать открытые окна»**. Добавится **только окно Scope Comparison**. Неизвестный/одинаковый/несовместимый Context либо отсутствие обоих Architecture на экране — отказ **без частичного изменения**.
8. В Scope Comparison выбор категории **events / requirements / work** сохраняется в настройках Scope, **не в State исходных Context**. Композицию можно восстановить после перезагрузки.
9. Для проверки независимого профиля нажмите **«▤ Markdown Profile»**. Документы и Context здесь редактируются без History. «+ Экран» и «+ Контекст» работают теми же общими операциями; возврат — **«← Симулятор»**. Старые A/B и Scope остаются сохранёнными отдельно.

Копии Context сохраняются в `pt006-simulator-context-copies-v1`, Scope instances — в **`pt006-simulator-comparison-scopes-v1`**, общая раскладка — в `pt006-simulator-multicontext-layout-v1`. Старые `pt006-simulator-content-[A|B]-v6` и `pt006-simulator-layout-[A|B]-v3` **сохраняют прежние назначения** и не удаляются при открытии общей рабочей области. Если пользователь менял старые A/B раскладки, общий Workspace при **первом** открытии импортирует их размещение как копии с контекстными адресами. Дальше общая раскладка редактируется и сохраняется отдельно.

## Где находится модель

```text
src/shell/workspace.ts                   Workspace v3 — только Screen/Panel/Tab/layout
src/shell/contexts.ts                    ResourceRef, ContextInstance/Template,
                                         контекстные адреса и привязка экранов
src/shell/contracts.ts                   WorkspaceProfile, ContentAddress,
                                         createContext/resolveContentAddress
src/shell/WorkspaceShell.tsx             generic + Контекст, + Экран, навигация/окна
src/shell/resourceProviders.ts            read-only разрешение ресурсов двух профилей
src/App.tsx                              выбор A/B / общего Workspace / Markdown
src/profiles/architecture-simulator/
  SimulatorProfile.tsx                   A/B State, независимые копии, сохранение,
                                         профильные представления и инспектор
  workspace.ts                           18 видов и 4 экранных рецепта
  scope-mechanisms/comparison.ts          typed Scope bindings/валидация/readout
  scope-mechanisms/ComparisonScopeView.tsx read-only результат и Scope-local выбор
src/profiles/markdown-fixture/             независимый Markdown Profile без History
```

Тип `Workspace` **по-прежнему версия 3**:

```ts
type Workspace = { version: 3; activeScreenId: string; screens: Screen[] }
type Panel = { id: string; rect: Rect; tabs: string[]; active: string | null }
```

Он хранит только визуальную компоновку. В новом режиме строковый таб-ID кодирует ссылку `context/<contextId>/<resourceId>` для **внутренней раскладки**; это **не** фактический ID доменного объекта и не замена структурированному `ResourceRef`. Функции `scopedContentId` / `parseScopedContentId` проверяют обратимое кодирование. На уровне действий `ContentAddress` может содержать `contextId`, Shell разрешает адрес через профиль и отвергает неизвестные источники без подстановки.

Каждый источник получает свой `ContentDescriptor` и ограничение `maxPerScreen`, поэтому окна A и B одного вида могут стоять рядом, не нарушая лимит вида **внутри одного Context**.

## Состояния и независимость

- **Legacy A/B Domain State и History** — разные `DemoStore`, сохранённые в существующих `content-v6` ключах. Snapshot/PlanRevision не переписываются из-за навигации или новых окон.
- **Новый Architecture Context** — `structuredClone` State A при создании; дальнейшее редактирование через вид/инспектор меняет **только свою копию**. `templateId`, `sourceId` и ID экземпляра хранятся отдельно.
- **Минимальный Context** — данные заметок без History. Не все 18 симуляторных видов имеют смысл для такого контекста.
- **Shared Layout** — один набор экранов может показывать несколько Context; закрытие вкладки/окна не удаляет State. Копирование экрана не создаёт копию данных.
- **Selections** — исторические cursors и выборы симуляции остаются **внутри каждого DemoStore Context**. Отдельный выбор фокуса Comparison хранится **в Scope instance**. Универсальная модель всех view-local selections ещё **не внедрена**.

**Область применения Scope:** `architecture-comparison-v1` имеет явные `participants.left/right: ResourceRef`, `allowedEffects: ['read']`, отдельный `presentation.contentId` и Scope-local `focus`. Валидация требует два разных доступных Architecture Context одного предметного сценария с совпадающими якорями. Результат рассчитывается при отображении из текущих источников; фактические данные, Plan и History **не изменяются**. Строковые вкладки Scope сохраняются как `scope/<scopeId>`.

**Совместимость:** историческое представление `comparison` в старом режиме **по-прежнему** использует исходные `allData.A/B` ради сохранения семантики `content-v6`. В общем Workspace встроенное legacy-представление `comparison` показывает инструкцию, как создать новый Scope Comparison; оно **не подменяется молча** старой парой A/B. Готовая/ручная композиции используют один и тот же механизм, хотя разные операции размещения. **Не реализованы:** универсальные права на запись/side effects, другие типы Scope, независимые межпрофильные механизмы и произвольные shared references. В G-CODE-04 проверено подключение второго профиля; **одновременный inter-profile Workspace** остаётся будущим расширением.

## Межпрофильный контракт: что доказано

В `src/shell/resourceProviders.ts` общий `ResourceRef` разрешается по `profileId/contextId/resourceId` через явно предоставленный read-only `ResourceProvider`. Профиль Architecture заявляет `architecture.read`, Markdown — `document.read`. Универсальная функция `inspectResources` может безопасно прочесть **два разных профиля** и вернуть два снимка, не меняя их State. Запрашиваемые семантические возможности проверяются отдельно; предметный `architecture-comparison-v1` **не принимает Markdown**. Это проверено unit-тестами. UI в текущей версии **переключает активный профиль**, а не открывает окна Architecture и Markdown вместе на одном Screen.

Markdown использует `pt006-markdown-contexts-v1` и `pt006-markdown-layout-v1`, не затрагивая `content-v6`, `layout-v3` и Scope экземпляры Architecture. Префиксы ключей разделены. [Профили и их контракты](../profiles/README.md).

## Неразрушающее восстановление сохранений (2026-10-11)

При загрузке сохранённых Workspace/Layout, Context/Scope и A/B/Markdown State приложение **не записывает резервные шаблоны поверх прежних ключей**. Если JSON или схема повреждены, интерфейс может показать безопасный резервный вид; исходный ключ остаётся неизменным до осознанного действия пользователя. Сохраняется **только изменившийся** State/Context/Layout, поэтому работа в Markdown не перезаписывает неактивные A/B данные. При попытке сохранить изменённый ресурс поверх невалидного сохранения утилита [safeStorage.ts](../../src/shell/safeStorage.ts) сначала делает точную копию исходных байтов в `pt006-recovery-original-v1:<исходный ключ>`; если архивирование не удалось, перезапись отменяется. Для восстановления повреждённого исходника можно вручную получить его из этого ключа через инструменты браузера — автоматическая исправляющая миграция не выполняется.

При загрузке частично повреждённого реестра копий Context и Scope валидные элементы используются независимо; остальные не принимаются в рабочее состояние. До следующего осознанного изменения **исходный реестр остаётся нетронутым**, а перед записью очищенного реестра исходная версия архивируется целиком. Scope по-прежнему применим только к совместимым источникам.

`Workspace v3` проверяет уникальность Screen/Panel ID, существование видов, конечную неотрицательную геометрию и технический минимум окна. Этот guard не объявляет будущую full schema/migration платформу уже реализованной. Markdown создаёт резервный экран для **реально восстановленного Context**, не предполагая существование `M-1`.

## Доказательства и совместимость

Для G-CODE-04 проверяются unit-тесты (включая legacy fixtures), сборка и линтер, браузерные сценарии старого Shell, Context, Scope Comparison и второго Markdown Profile. В контекстном browser smoke проверяются два обычных Architecture на одном экране, переход из B в B, отдельное редактирование копии и сохранение минимальных заметок без History, reload и возвращение к прежним A/B. Сценарий `scope-ui-smoke.cjs` проверяет ready/manual сборку, негативную применимость, reload Scope и отсутствие записей в A/B. `profile-universality-ui-smoke.cjs` проверяет отдельные Markdown Context, generic Shell, изменение State, сохранение после reload и обратное переключение на симуляцию без потери A/B. Новые негативные тесты: `recovery.test.mjs` (архивирование raw bytes, валидность Workspace, Markdown без M-1) и `recovery-ui-smoke.cjs` (реальные отдельные Edge-профили, повреждённые A/layout, частичные Context/Scope registries и reload). Датированные результаты тестов — в [актуальном статусе проекта](../../README.md).

Миграции legacy `v5/v4/v3`, правила сохранения фактической истории и исходные fixture описаны в [датированном журнале PT-006](../../../PT006_REMEDIATION_2026-10-10.md). Не путать **новую независимую общую раскладку** с необратимой миграцией старых layout.
