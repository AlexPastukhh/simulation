# Workspace — текущая реализация PT-006

**CURRENT / G-CODE-02, 2026-10-11.** В PT-006 теперь доступны **два режима одного профиля Architecture Simulator**: прежние отдельные A/B раскладки и новый **«Общий Workspace»** с несколькими Context. Это не готовая многопрофильная система и не Scope Engine. [Shell](../shell/README.md) · [план остальных этапов](NEXT_CODE_PLAN_CANDIDATE.md).

## Как пользоваться

1. В верхней панели нажмите **«⊞ Общий Workspace»**. Первый запуск создаёт **отдельную** общую раскладку из сохранённых A и B раскладок; старые ключи/экраны не удаляются. Кнопка «← Отдельные A/B раскладки» возвращает прежний интерфейс.
2. Выберите экран **A · Архитектура и реализация**, создайте окно **«+ Окно»** и через каталог содержимого добавьте **B · Architecture**. Теперь обычные Architecture A и Architecture B видны одновременно на **одном** Screen. Переходы из B остаются привязанными к B; переходы из A — к A.
3. Нажмите **«+ Контекст»** и выберите **«Эволюция архитектуры»**. Создаётся новый Context с **независимой рабочей копией текущего State A**, его provenance и четырьмя обычными тематическими экранами. Данные A/B от этого не изменяются.
4. Другой вариант **«Минимальный контекст»** создаёт один экран с редактируемыми требованиями/заметками, **без History**. Содержимое сохраняется независимо и доступно после перезапуска.
5. **«+ Экран»** по-прежнему делает пустой экран или копию текущего: это изменение представления, не копирование Context или State.

Копии Context сохраняются в `pt006-simulator-context-copies-v1`, общая раскладка — в `pt006-simulator-multicontext-layout-v1`. Старые `pt006-simulator-content-[A|B]-v6` и `pt006-simulator-layout-[A|B]-v3` **сохраняют прежние назначения** и не удаляются при открытии общей рабочей области. Если пользователь менял старые A/B раскладки, общий Workspace при **первом** открытии импортирует их размещение как копии с контекстными адресами. Дальше общая раскладка редактируется и сохраняется отдельно.

## Где находится модель

```text
src/shell/workspace.ts                   Workspace v3 — только Screen/Panel/Tab/layout
src/shell/contexts.ts                    ResourceRef, ContextInstance/Template,
                                         контекстные адреса и привязка экранов
src/shell/contracts.ts                   WorkspaceProfile, ContentAddress,
                                         createContext/resolveContentAddress
src/shell/WorkspaceShell.tsx             generic + Контекст, + Экран, навигация/окна
src/App.tsx                              выбор «старые A/B» / «Общий Workspace»
src/profiles/architecture-simulator/
  SimulatorProfile.tsx                   A/B State, независимые копии, сохранение,
                                         профильные представления и инспектор
  workspace.ts                           18 видов и 4 экранных рецепта
```

Тип `Workspace` **по-прежнему версия 3**:

```ts
type Workspace = { version: 3; activeScreenId: string; screens: Screen[] }
type Panel = { id: string; rect: Rect; tabs: string[]; active: string | null }
```

Он хранит только визуальную компоновку. В новом режиме строковый таб-ID кодирует ссылку `context/<contextId>/<resourceId>` для **внутренней раскладки**; это **не** фактический ID доменного объекта и не замена структурированному `ResourceRef`. Функции `scopedContentId` / `parseScopedContentId` проверяют обратимое кодирование. На уровне действий `ContentAddress` может содержать `contextId`, Shell разрешает адрес через профиль и отвергает неизвестные источники без подстановки.

Каждый источник получает свой `ContentDescriptor` и ограничение `maxPerScreen`, поэтому окна A и B одного вида могут стоять рядом, не нарушая лимит вида **внутри одного Context**.

## Состояния и независимость

- **Legacy A/B Domain State и History** — разные `DemoStore`, сохранённые в существующих `content-v6` ключах. Snapshot/PlanRevision не переписываются из-за навигации или новых окон.
- **Новый Architecture Context** — `structuredClone` State A при создании; дальнейшее редактирование через вид/инспектор меняет **только свою копию**. `templateId`, `sourceId` и ID экземпляра хранятся отдельно.
- **Минимальный Context** — данные заметок без History. Не все 18 симуляторных видов имеют смысл для такого контекста.
- **Shared Layout** — один набор экранов может показывать несколько Context; закрытие вкладки/окна не удаляет State. Копирование экрана не создаёт копию данных.
- **Selections** — подготовленные исторические cursors и часть выбранных элементов остаются **внутри каждого DemoStore Context**. Универсальная модель view-local selections ещё **не внедрена**; её семантика требует дальнейшей работы.

**Ограничение:** профильное представление `comparison` пока использует подготовленные `allData.A/B`, а не явные Scope bindings. Готовая A+B композиция с общими инструментами и ручная сборка сравнения относятся к [G-CODE-03](NEXT_CODE_PLAN_CANDIDATE.md). Взаимодействие между **разными профилями** относится к G-CODE-04.

## Доказательства и совместимость

Для G-CODE-02 проверяются unit-тесты, сборка и линтер, отдельные браузерные сценарии старых экранов и нового режима. В контекстном browser smoke проверяются два обычных Architecture на одном экране, переход из B в B, отдельное редактирование копии и сохранение минимальных заметок без History, reload и возвращение к прежним A/B. Датированные результаты тестов — в [актуальном статусе проекта](../../README.md).

Миграции legacy `v5/v4/v3`, правила сохранения фактической истории и исходные fixture описаны в [датированном журнале PT-006](../../../PT006_REMEDIATION_2026-10-10.md). Не путать **новую независимую общую раскладку** с необратимой миграцией старых layout.
