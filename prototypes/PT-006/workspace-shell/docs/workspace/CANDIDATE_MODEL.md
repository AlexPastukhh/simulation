# Кандидатная архитектура Workspace, контекстов и Scope Mechanisms

**Статус: CANDIDATE для дальнейшего расширения архитектуры; группы G-CODE-01–04 реализуют оговорённую проверяемую часть.** Уже работают независимые Context, один Context Template из четырёх экранов, минимальный Context без History и одновременное отображение A/B. **Один read-only `architecture-comparison-v1` с явными bindings и готовой/ручной сборкой реализован. Другие Scope Mechanisms, shared-reference writes и одновременный межпрофильный Workspace ещё не реализованы. G-CODE-04 добавил независимый Markdown Fixture и read-only контракт разрешения ресурсов двух профилей**. Текущий факт описан в [Workspace](README.md), дальнейшие шаги — в [плане](NEXT_CODE_PLAN_CANDIDATE.md). Этот документ сохраняет кандидатный статус всего ещё не принятого архитектурного набора.

## Суть

**Profile** предоставляет определения типов контента, JSON Schema, представления, предметные операции, шаблоны и подготовленные контексты.

**Context** — конкретный осмысленный рабочий набор с назначением, ресурсами и заданным или связанным State. Он может содержать черновой Plan, начальные требования или полноценную симуляцию с History; **полнота и History не обязательны**. «Готовый» означает «пригодный для начала или продолжения работы», а не «завершённый».

**Workspace** — среда, где пользователь инстанцирует и подключает контексты, работает с их ресурсами и связывает инструменты. Контексты могут использовать определения разных профилей. **Screen** и **Window/Tab** — способы показа этих ресурсов, а не их владельцы: один экран может показывать несколько контекстов, а один контекст — несколько экранов.

```text
PROFILE LIBRARY                         WORKSPACE (целевая модель)
├─ Architecture Simulator Profile      ├─ подключённые профили/возможности
│  ├─ типы и виды                        ├─ Context A (ресурсы, State, History?)
│  ├─ предметные инструменты            ├─ Context B (ресурсы, State, History?)
│  ├─ Context Template                   ├─ Context C (например, документы)
│  │  └─ начальные 4 экрана              ├─ связи и настроенные инструменты
│  └─ Prepared Context A/B               └─ экраны Workspace
├─ Markdown Fixture (CURRENT, отдельный активный профиль)       └─ A Architecture | B Architecture | Compare(A,B)
└─ межпрофильные определения
                         Shell: открыть, найти, показать, разместить, навигировать
```

Это **не дерево обязательного владения**: профиль может быть источником определения, контекст владельцем/связующей областью State, а экран — общим представлением.

## Шаблон, готовый контекст и композиция

**Context Template** — повторно используемый рецепт создания рабочего контекста: ожидаемые ресурсы, ссылки, необязательный seed State, инструменты и рекомендуемый **набор экранов**. В G-CODE-02 четыре экрана Architecture Simulator уже предоставляются **вместе как один Context Template**, а не четырьмя предметными пунктами «+ Экран». После создания экраны остаются обычными настраиваемыми экранами Workspace, их закрытие не уничтожает Context.

**Prepared Context** — подготовленный экземпляр или snapshot с конкретным State. Это может быть минимальная база для планирования приложения либо полная authored simulation архитектуры. Нужно различать импорт **копии** и подключение **ссылки** на исходный ресурс; предпочтение — рабочая копия с provenance, явные shared resources по ссылкам.

**Prepared Multi-context Composition** — кандидатный рецепт одновременного развёртывания нескольких Context, привязок, инструментов и экранов. Пример: сравнительная симуляция A+B. Предпочтительный подход — композиция нескольких контекстов, а не обязательный новый вложенный `CompositeContext`. Этот выбор ещё не committed.

**Постепенная сборка** использует те же возможности: сначала Context A, потом B, затем настроенный инструмент Comparison. Готовый и ручной пути не должны требовать разных скрытых движков сравнения.

## Scope Mechanism — не просто поле scope

**Scope Mechanism** — определение переиспользуемого взаимодействия: какие сущности могут участвовать, какие источники связать, какие действия разрешены, какие эффекты возможны и как направить результат. **G-CODE-03 CURRENT:** один профильный `architecture-comparison-v1` уже обеспечивает read-only пары совместимых Architecture Context с отдельным Scope Instance и сохранённым фокусом. Всё остальное в этом разделе — кандидатная генерализация. **Scope Instance** — конкретная настроенная область участников, привязанная к рабочим ресурсам. Инструмент может иметь одну или несколько привязок.

У Scope Mechanism различаются:
- **область доступности и разрешений** — где и кем механизм может применяться;
- **область источников/участников** — какие ресурсы и контексты участвуют;
- **область эффекта** — какой State механизм читает, изменяет или создаёт, где хранит результат;
- **область представления** — в каком окне или экране показать результат.

Scopes могут пересекаться, поэтому их нельзя вывести из одной физической иерархии `Screen → Window → Tab`. Одно окно может участвовать в нескольких Scope, а действие — работать с ресурсами без открытого окна. **Механизмы связывают ресурсы, а не координаты окон.**

### Логическое размещение определений (предложение, не существующие каталоги)

```text
src/
├─ shell/
│  └─ scope-mechanisms/              # предметно-независимые базовые механизмы
├─ profiles/
│  └─ architecture-simulator/
│     └─ scope-mechanisms/
│        ├─ architecture-comparison/ # A/B одного профиля: межконтекстно,
│        │                          # но НЕ межпрофильно
│        └─ scenario-specific/
│           └─ booking-simulation/   # только для совместимого сценария
└─ integrations/
   └─ scope-mechanisms/
      └─ architecture-to-markdown/   # зависимости от нескольких профилей
```

Реально создана **только** профильная папка `src/profiles/architecture-simulator/scope-mechanisms/` для Comparison; в Shell есть отдельный read-only [resourceProviders.ts](../../src/shell/resourceProviders.ts), но **папок** Shell/integrations Scope из схемы нет. Markdown Fixture расположен в `src/profiles/markdown-fixture/` без предметных механизмов сравнения. Создавать отдельные `general`, `context-specific`, `scenario-specific` следует **только при реальной потребности**, без пустых каталогов.

**Главное правило принадлежности:** механизм одного профиля может работать между несколькими его контекстами и оставаться в этом профиле; интеграционный механизм относится к отдельной межпрофильной области. Узкие механизмы организуются подпапками по контексту, типу контекста или сценарию. Однако **папка только обозначает специализацию; запрет применения проверяет исполняемый контракт**. Контракт не должен опираться исключительно на совпадение JSON Schema: похожая форма не гарантирует одинакового смысла.

**Владелец исполнения:** универсальная инфраструктура Shell/Workspace разрешает адреса, проверки доступности и маршрутизацию; профиль или интеграция обеспечивает предметную логику. Настройки конкретной области и результата принадлежат рабочей композиции, определения — поставщику. Сами Scope Mechanisms не должны становиться владельцами доменных данных.

## Разделение идентичности и состояний (пока направление)

Не смешивать **идентификатор типа**, **конкретный ресурс**, **исторический snapshot**, **контекст** и **вкладку**. Будущий View может иметь несколько входов: `Architecture A`, `Architecture B` или `Requirement + Markdown`.

Отдельно хранить по реальному смыслу: предметный Domain State; подготовленную History; общие синхронизированные выборы контекста; локальное состояние представления; раскладку; настроенные входы/результаты инструмента. Переход `open-content` не должен создавать фактические события или автоматически исполнять Evolution Steps. Прямое редактирование State не переписывает подготовленную историю.

## Статус и нерешённые развилки

- **CURRENT G-CODE-02:** прежний режим A/B раскладок сохранён; в отдельном общем Workspace обычные Architecture A и B видны на одном экране, Context Templates создают независимые копии State, а минимальный Context хранит заметки без History.
- **CURRENT после G-CODE-03:** явные bindings и проверка применимости одного read-only Comparison двух совместимых Architecture Context, готовая A+B и последовательная ручная сборка с двумя открытыми Architecture и отдельным result-window. **Кандидат:** универсальные Scope и permissions, полный Workspace registry, произвольные view-local настройки и межпрофильные интеграции. В текущем коде таб-ID всё ещё хранится как контекстно-адресованная строка layout-v3.
- **Выбрано и реализовано по умолчанию:** новый Context получает **копию** State, явно общие ссылки не создаются автоматически. **Открыто:** контракт действительно разделяемых ресурсов и разрешений, shared selections vs view-local настройки, группировка экранов, семантическая совместимость инструментов.
- **CURRENT G-CODE-04:** подключён второй **Markdown Fixture Profile** через тот же интерфейс Shell, с отдельными Context, layout и редактируемым документом без History. Публичный read-only `ResourceProvider` разрешает `ResourceRef` обоих профилей и проверяет заявленные семантические capabilities. Тестовый просмотр снимков двух профилей возможен **через контракт**, но UI сейчас только переключает активные профили; Architecture Comparison не принимает Markdown.
- **Не реализовано после G-CODE-04:** общий многопрофильный Workspace с окнами разных профилей одновременно, динамический каталог произвольных профилей, универсальный Scope Engine, эффекты записи/общие изменяемые ресурсы, принудительная миграция content-v6/layout-v3 и папки Shell/integrations Scope. Текущая поставка доказывает узкую универсальность без принятия всей будущей модели.
