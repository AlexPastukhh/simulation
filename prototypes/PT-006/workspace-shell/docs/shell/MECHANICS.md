# Core и Scope-механики: подключение и наблюдение

Кнопка **«Механики»** в панели экранов показывает весь Workspace. Кнопка ⌁ в заголовке окна ограничивает показ его текущим представлением. Инспектор доступен и при скрытой верхней панели, и в режиме просмотра.

## Границы владельцев

| Сущность | Чем владеет |
|---|---|
| Content Instance | Предметными данными. Несколько представлений читают одного владельца |
| Представление | Проекцией Content и своими локальными настройками; новый владелец данных не создаётся |
| Window / Panel | Вкладками, активным видом и геометрией |
| Screen | Размещением окон |
| Screen Group в layout | Порядком и группировкой кнопок экранов в rail |
| Подключение Scope-механики | Участниками, областью действия и собственными настройками механики |

Физическая группировка rail не задаёт автоматически семантический Scope. Перемещение окна не перепривязывает его источники. Закрытие представления не удаляет предметный Content или общий навигационный Scope.

Актуальные владельцы и виды перечислены в [CONTENT_VIEWS](../architecture-simulator/CONTENT_VIEWS.md). Состав четырёх экранов и ключи browser storage определены в [Workspace](../workspace/README.md); здесь они не дублируются.

## Определение, подключение и вызов

- **Definition** — код и контракт механики: назначение, уровень, разрешённые эффекты и исходники.
- **Connection / Scope Instance** — конкретное подключение: стабильный ID, реальные участники, область, presentation и владелец настроек.
- **UI binding** — привязка открытого элемента к обработчику из текущей сборки. Закрытый UI не означает отсутствие настроенного подключения.
- **Invocation** — записанный фактический вызов. Наличие Definition или Connection не доказывает, что вызов состоялся.

В «Подключено» для core «Открыть Content» показываются возможные связи кнопок **всех размещённых представлений на всех экранах**, даже если экран не смонтирован или вкладка неактивна: подпись кнопки, экран, окно, Content-источник, ссылка на исходник и цель открытия. Владелец кнопки указан непосредственно у её JSX-обработчика (атрибут data-mechanics-views), без отдельной таблицы маршрутов; цель буквального вызова open('contentId') извлекается TypeScript AST. Если размещено несколько окон одного Content, указаны отдельные места. Существующее окно для цели ищется тем же helper, что использует Shell openContent; иначе указывается создание нового окна на активном экране. При открытии через ⌁ список по умолчанию ограничен окном; кнопка «Показать все экраны» расширяет его до всего Workspace без выполнения действий. Несмонтированный элемент помечен как предусмотренная кодом точка входа: это не доказательство его текущей доступности или фактического вызова. Для других Core/Scope-подключений показываются наблюдаемые DOM-элементы текущего экрана и код известных обработчиков; неизвестный эффект не угадывается.

«Подключено» и «Определения» — разные разделы одного Inspector. Карточка подключения показывает участников, разрешённые эффекты, представления результата, доступность и состояние сейчас. Guard записи повторно проверяется самим writer; сведения Inspector не дают права обойти его.

Core-механики открывают Content и управляют окнами, вкладками, экранами, группами, геометрией и сохранением Workspace. Они предоставляются Shell независимо от предметного профиля. Профиль подключает предметные механики через [WorkspaceProfile](../../src/shell/contracts.ts). Профиль без описаний своих механик сохраняет core-возможности; это не доказывает покрытие его предметной логики.

## Размещение Scope-механик в исходниках

Определение хранится у реального шаблона, который задаёт соответствующий Scope:

| Владелец / механизм | Исходник |
|---|---|
| Группа экранов профиля: Event/Step navigation | [template.ts](../../src/templates/profiles/single-architecture/screen-groups/application-architecture/template.ts), соседняя папка [scope-mechanisms/history-and-plan-navigation](../../src/templates/profiles/single-architecture/screen-groups/application-architecture/scope-mechanisms/history-and-plan-navigation/definition.ts) |
| Профиль: предметное редактирование | [content-edit/definition.ts](../../src/templates/profiles/single-architecture/scope-mechanisms/content-edit/definition.ts) |
| Представление Explorer: выбор объекта | [object-selection/definition.ts](../../src/templates/profiles/single-architecture/views/explorer/scope-mechanisms/object-selection/definition.ts) |
| Представление Impact History: фильтр цели | [target-filter/definition.ts](../../src/templates/profiles/single-architecture/views/impact-history/scope-mechanisms/target-filter/definition.ts) |
| Markdown Content: редактирование | [edit/definition.ts](../../src/templates/content/markdown-document/scope-mechanisms/edit/definition.ts) |

Для нового механизма конкретного Content, Window или Screen действует тот же принцип: папка scope-mechanisms у соответствующего настоящего шаблона. Пустые папки для всех возможных scopes не создаются. Произвольный пользовательский preset окна не требует нового исходника в src.

Общий core и общие helpers остаются общими. Renderer связывает элемент с действующей функцией; определение ссылается на эту функцию. Общие writer/validation/geometry helpers не копируются в каждую папку Scope. Только специфичная навигационная логика перенесена в [mechanic.ts](../../src/templates/profiles/single-architecture/screen-groups/application-architecture/scope-mechanisms/history-and-plan-navigation/mechanic.ts).

Исходники определения не содержат выбранный пользователем ивент. Настройки конкретного подключения хранятся отдельно от определения, layout и предметных данных.

## Действующие подключения single-architecture

**Event / Step navigation** — Scope связанных представлений группы четырёх экранов. Курсор задаёт исторический факт и CURRENT/Step. Сохранённый фактический снимок и план при просмотре не изменяются; Step не исполняется.

Повторные наборы экранов остаются **зеркальными**: это другие размещения тех же Content и того же навигационного подключения. Создание набора или группировка rail не создаёт независимый курсор. Независимые курсоры при общих данных потребуют отдельного изменения модели подключений и проверки writer guards; это поведение здесь не реализовано.

**Content edit** — запись Architecture Planning, Requirements и Materials. Доступность использует тот же editBlockReason, который вызывается writer. Исторический режим, validation, Web Locks, stale bytes, архив и read-back не заменяются логикой Inspector.

**Markdown edit** — самостоятельный writer документов; исторический cursor архитектуры не превращает Markdown в исторический снимок.

**Explorer / Impact History filter** — локальное состояние отдельного представления в отдельном окне. Смена вида или закрытие сбрасывает это состояние. Фильтр Explorer не переносится в Impact History. Если цель Impact History отсутствует в выбранном срезе, control и фактический фильтр оба показывают «Все изменения».

## Исходники и покрытия

[mechanicsSourcePlugin](../../dev/mechanicsSourcePlugin.ts) строит индекс из собственных TS/TSX-файлов src и dev данного приложения. Он добавляет UI-обёртки и source IDs при сборке, без отдельного ручного списка кнопок. Обёртка вызывает исходный обработчик один раз, сохраняет его результат/Promise и не повторяет команду ради наблюдения.

Shell получает короткий индекс. Тексты исходников и UI Inspector загружаются при открытии. Произвольного endpoint чтения файлов нет; пользовательские browser данные не входят в source index.

Показан authored TS/TSX исходник соответствующей сборки, его hash, точное место обработчика и статические локальные зависимости. Статический граф импортов не доказывает выполнения каждого модуля. После HMR новый индекс обновляется; вызов со старым hash помечается как относящийся к другому коду. Текст старого исходника не выдаётся за текст новой версии.

«Выбрать элемент» открывает его обработчик, подавляя действие выбранного элемента. Обычные действия работают без этого режима. Сама панель не записывает свои действия; её исходники доступны в общем списке. «Покрытие» отличает текущие DOM bindings от найденных в коде effects/listeners/timers/observers/writes. Автоматический source audit не означает полный JS debugger: внутренности React/браузера и каждый промежуточный callback native listener не трассируются пошагово.

## Фактические вызовы

Запись включается явно в «Вызовы» и хранит последние 200 записей в памяти текущего Shell. Она не пишет Content, History, localStorage, GitHub или внешнюю telemetry.

| Отметка | Что подтверждено |
|---|---|
| Callback вызван / завершён | Обработчик был вызван; это не подтверждение сохранения |
| Ожидание | Async callback или writer ещё не подтвердил результат |
| Наблюдалось | Зафиксирована конкретная commit/drag точка; это не автоматически domain write |
| Read-back подтверждён | Реальный writer или preserving helper проверил сохранённые bytes |
| Отклонено / ошибка / отменено | Наблюдался соответствующий результат; success не подставляется |

Command reducer остаётся чистым: диагностические replies входят в его результат и читаются после commit/persistence. Близкие layout действия могут объединяться в один React commit; журнал не заявляет отдельное отображение каждого промежуточного состояния. Async Content writer сообщает saved после read-back и перед публикацией нового Content state.

До включения записи история действий не восстановлена. Неподтверждённое pending не означает success. Очистка журнала и закрытие Inspector не меняют пользовательские данные.
