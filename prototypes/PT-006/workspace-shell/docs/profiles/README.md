# Профили — подключаемое содержимое Workspace

**CURRENT / опубликованный Git `main`, с пометками о локальной неопубликованной итерации.** Профиль предоставляет Shell описание содержимого, рендеринг и предметное поведение. Это **не** самостоятельный рабочий Workspace. В текущем прототипе подключён только [Architecture Simulator](architecture-simulator/README.md).

## Реальный контракт подключения

[src/shell/contracts.ts](../../src/shell/contracts.ts) определяет `WorkspaceProfile`. В нём профиль сообщает `id`, `title`, `descriptors`, `initialWorkspace`, `contextId`, `contexts`, ключи локального layout, обработчики миграции, `renderContent`, `renderPanelTools`, инспектор и профильные команды. В **локальных неопубликованных правках** к этому контракту добавлены опциональные `screenTemplates` и `screenBundles`: это рецепты **раскладок экранов**, не самостоятельные предметные контексты. В опубликованном `main` этих полей и меню пока нет.

[src/App.tsx](../../src/App.tsx) вызывает `useSimulatorProfile()` и передаёт результат в `WorkspaceShell`. Это **один активный профиль**, а не система динамического подключения множества провайдеров.

**Shell знает**, как открыть зарегистрированный вид, разместить окно и сохранить раскладку. **Профиль знает**, как устроены доменные State, JSON Schema, подготовленная история и команды предметной модели. История не обязана присутствовать у каждого будущего профиля.

## Доступные и возможные профили

- **Реализовано:** [Architecture Simulator](architecture-simulator/README.md) — 18 видов, A/B authored fixture, требования, Plan, архитектура, State/Schema/History, переходы к другим видам.
- **Пример возможности, не реализовано:** Markdown-документы и их редактор. Универсальность строковых идентификаторов проверялась синтетическими тестовыми дескрипторами, **реального Markdown-профиля пока нет**.
- **Кандидат:** другие типы контента, шаблоны/готовые контексты, предметные Scope Mechanisms и взаимодействия между профилями. Они не являются частью действующего `WorkspaceProfile` runtime.

## Кому принадлежат Scope Mechanisms в целевой архитектуре

Это **не текущая структура исходников**, а [кандидатный принцип](../workspace/CANDIDATE_MODEL.md):

- предметно-независимые механизмы → Shell;
- механизмы одного профиля, даже между двумя контекстами этого профиля → соответствующий `profiles/<profile>/scope-mechanisms/`;
- механизм, требующий определения/контрактов двух профилей → `integrations/scope-mechanisms/`;
- механизм, годный только для конкретного сценария или класса контекстов → узкая подпапка у владельца и **исполняемая проверка применимости**, а не только название папки.
