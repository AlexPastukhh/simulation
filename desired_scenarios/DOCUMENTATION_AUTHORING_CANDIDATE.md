# Desired Real-Life Definition — создание и уточнение документации

**Редакция:** 2026-10-11. **Статус:** CANDIDATE / TRANSACTION OPEN. Связанный самостоятельный сценарий из [набора DRLD](README.md), а не обязательный этап каждого просмотра.
**Применимые Need/FR:** общесистемный Need ещё не получил согласованного ID. Контракты Gendocen и правдивость статусов используются как контекст; они не становятся новыми глобальными FR. См. [матрицу](NEED_FR_TRACE_REVIEW_CANDIDATE.md).

## Fundamental Benefit of Scenario

**Кому и ради чего:** мне как автору и последующему читателю нужна содержательная документация, пригодная к дальнейшему повторному использованию человеком, ИИ и визуальными представлениями, без постоянного ручного согласования одинаковых фактов.
**Где польза появляется:** после создания пригодного канонического фрагмента она уже доступна читателю; когда структурированные поля и их зависимости определены, материал становится пригоден и для повторного машинного использования; после проверки изменений снижается риск использовать устаревшие производные результаты.
**Observable evidence:** можно указать канонический источник и его предназначение; документ читаем или структурный объект соответствует доступным контрактам, а сомнительные утверждения и необходимость пересборки не маскируются.

## Scenario Concept

Автор выбирает форму документации под задачу: свободный Markdown либо структурированный JSON с правилами Gendocen. Он или ИИ готовит каноническое содержимое, проверяет форму и значимые последствия изменения; при необходимости движок пересобирает зависимые объекты и представления. Не требуется создавать специальный редактор в Workspace.

## Detailed Desired Real-Life Scenario

**Исходное положение:** у пользователя возник новый факт, требование, решение, план или учебный материал; репозиторий доступен для разрешённой работы. Участники — автор и, по желанию, ИИ-помощник. Есть существующий документ либо место для нового. Для структурированного пути доступны проектные схемы, поля, зависимости и при необходимости builder; если нет — их подготовка является отдельным усилием и не подразумевается мгновенной.

1. **Определяю содержательную цель и канонический источник.** Что нужно сохранить, для кого и в какой проект/документ? Если существующее содержание уже подходит, не создаю дубликат ради интерфейса.
2. **Выбираю минимально достаточную форму.** Обычная заметка может остаться Markdown. Если нужны адресуемые поля, вычисляемые данные, повторное использование или строгая структура для ИИ — выбираю подходящий JSON-ресурс и контракт.
3. **Пишу или изменяю материал.** Я или ИИ работаем с каноническим Markdown, raw JSON либо определением вычислений, а не правим сгенерированный Markdown как источник истины. Польза от подготовки возникает по мере появления пригодных содержательных частей.
4. **Проверяю.** Смотрю на структуру, ссылки, релевантные зависимости и источники утверждений. Формальная валидность не означает предметную истинность; при содержательных сомнениях человек/ИИ отдельно рассматривает их.
5. **Обновляю затронутые результаты, если необходимо.** Изменившиеся входы могут требовать пересборки зависимых объектов и Markdown. Для обычного Markdown специальная сборка необязательна. Пользователь различает состояние «готово», «нужна пересборка/ревью», «не удалось».
6. **Использую пригодный документ.** Материал можно прочитать, передать соответствующему процессу сборки или открыть для визуального исследования. Вариант Git commit/push выбирается в существующем рабочем процессе; запись через Workspace не предпосылка данного сценария.

**Альтернативы, ошибки, восстановление:** при отсутствии нужной схемы не подделывается соответствие — допускается plain Markdown или отдельная подготовка контракта; при ошибке проверки остаётся возможность исправить источник; при ошибке сборки не объявляется обновлённым производный результат; при неоднозначности/непроверенном утверждении отмечается необходимость ревью. Публикация может быть отложена, если проект ещё не готов.

**Реальные costs:** время на авторство, построение/обслуживание схем и builder-правил, проверки, ревью ИИ-результата, исправление ошибок и возможное ожидание сборки/Git-операций. Сценарий не предполагает, что такие накладные расходы оправданы для каждой заметки. Частота, сроки и суммы неизвестны; трудозатраты разработки самого приложения сюда не включаются.

**Связанные сценарии:** [объекты Gendocen](GENDOCEN_OBJECT_COMPOSITION_CANDIDATE.md) и [Workspace](WORKSPACE_VISUALIZATION_CANDIDATE.md) могут потреблять результат этого пути; обратной рекурсивной зависимости нет. В Gendocen plain Markdown каноничен; materialized Markdown производится из структурированных объектов. Конкретная интеграция с Workspace остаётся открытой.
