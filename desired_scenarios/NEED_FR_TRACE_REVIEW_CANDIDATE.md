# Review trace — User Need / Fundamental Requirements / Desired Real-Life Definitions

**Дата:** 2026-10-11. **Статус:** REVIEW / CANDIDATE; эта таблица не вводит новые N-/FR-* и не повышает старые candidate до committed.
**Назначение:** показать, какие сформулированные Need/FR применимы к конкретным DRLD, где охват не установлен и где не следует путать Desired Path с реализационными средствами.

## 1. Общая нужда системы — пока без формального ID

**Прямые пользовательские источники:** Git-банк документации; обычные Markdown и структурированные JSON; Gendocen собирает объекты с зависимыми полями и генерирует Markdown; Workspace должен удобно отображать самые разные знания и сценарии, включая проектное планирование; ИИ опирается на контракты; архитектурная эволюция — лишь одно предметное применение.

**Краткая реконструкция для анализа, не новый committed Need:** пользователь хочет переиспользуемую удобную среду для создания, изучения и визуального исследования своей документации/проектов без разрозненных самостоятельных приложений и без ручного согласования одинаковых структурированных данных. Эта фраза ещё не принята как формальный N-*.

**Покрытие DRLD:** [общий путь](../DESIRED_SCENARIO_DOCUMENTATION_WORKSPACE_CANDIDATE.md); [авторство](DOCUMENTATION_AUTHORING_CANDIDATE.md); [зависимые объекты](GENDOCEN_OBJECT_COMPOSITION_CANDIDATE.md); [визуализация](WORKSPACE_VISUALIZATION_CANDIDATE.md). Все четыре связаны, но каждая описывает собственную пользу и реальный путь.

**Открыто:** формальный реестр общесистемных Needs, набор применимых Fundamental Requirements, приоритеты и принятие. Поэтому утверждать, что полнота FR доказана, нельзя.

## 5. Кандидатные инварианты, не новая FR-нумерация

- Источник знания должен оставаться идентифицируемым: plain Markdown, raw JSON, derived object и состояние конкретного UI-вида не следует молча смешивать.
- Неактуальный/недоступный ресурс нельзя без объяснения показывать как подтверждённо актуальный; точная политика fallback и восстановления ещё не согласована.
- Структурный контракт ИИ и вычисляемые зависимости не доказывают истинность предметного утверждения.
- Универсальное отображение не означает обязательность симуляции, History, автоматического планировщика или Scope у всех документов.
- Сложный инструмент используется только для совместимых данных, однако механизм проверки совместимости не утверждён.
- Визуализация реального планирования приложения/игры должна **по возможности переиспользовать документируемые Requirements, Architecture, Plan, Evolution Steps, Impact**, если они применимы, а не автоматически всю A/B-историю симулятора.

Это **кандидатные следствия review**, часть основана на прямом пользовательском направлении, часть — осторожные интерпретации. Нужны отдельная проверка формулировок, происхождения, необходимости и scope прежде чем переводить что-либо в FR.

## 6. Непокрытые вопросы и границы

**Сценарные вопросы:** долгоживущая рабочая ситуация и продолжение исследования; подходящий жизненный цикл документов, необходимость создания/публикации из Workspace; реально используемые виды планирования; степень автономности и взаимосвязей профильных сценариев; роль ИИ в цикле авторства.

**Реализационные вопросы (НЕ DRLD и не FR по умолчанию):** transport/API к объектам Gendocen, формат материализованного JSON, конкретный профильно-ориентированный View Registry, межпрофильные окна, shared resources, безопасность Python и cache policy. Их нужно проверять по целевому пользовательскому пути и собственным ограничениям.

**Governance:** не вводить новые глобальные FR без отдельного основания; не объявлять v6 DRLD, Git-коммит, модель Gendocen или PT-006 новым semantic commitment. [Индекс текущих DRLD](README.md).
