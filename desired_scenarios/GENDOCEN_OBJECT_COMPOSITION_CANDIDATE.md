# Desired Real-Life Definition — получение зависимых объектов Gendocen

**Редакция:** 2026-10-11. **Статус:** CANDIDATE / TRANSACTION OPEN. Самостоятельный сценарий получения согласованных данных, а не описание только внутреннего builder-процесса.
**Need/FR:** связан с общей нуждой многократного использования структурированной документации; нового N-/FR-ID не присвоено. [Карта](NEED_FR_TRACE_REVIEW_CANDIDATE.md).
**Текущая техническая граница:** Python API/CLI Gendocen могут строить derived objects; готового live API для React Workspace не заявлено.

## Fundamental Benefit of Scenario

**Кому и ради чего:** автору/потребителю структурированной документации нужен пригодный объект с согласованными значениями полей, часть которых зависит от других ресурсов. Польза — отсутствие ручного пересчёта этих полей и возможность использовать результат для Markdown либо подходящего UI.
**Где проявляется:** уже при первом получении требуемого вычисленного значения/объекта; повторяется после изменения входов и повторной сборки, когда пользователь может опираться на новое актуальное значение.
**Проверяемый эффект:** известны идентичность объекта, доступные значения, источники/зависимости в пределах возможностей движка и состояние актуальности; результат можно передать потребителю без ручного переноса значений.

## Scenario Concept

Пользователь или обслуживающий его процесс обращается к структурированному ресурсу проекта. Gendocen использует исходные значения и зарегистрированные вычисления, собирает объект и при необходимости материализует из него документ. При изменениях входов важно отличать вычислительное обновление от проверки смысла. UI может использовать объект напрямую через ещё не выбранный способ передачи.

## Detailed Desired Real-Life Scenario

**Исходная ситуация:** в доступном Git-проекте есть JSON-ресурс, нужные зависимости и при необходимости проектные builder-правила. Пользователю нужен готовый результат: значение/объект или Markdown. Для обычного plain Markdown этот путь не нужен. Доверие к исполняемому проектному Python, доступ к данным и возможность запуска процесса являются существенными предпосылками.

1. **Выбираю полезный результат.** Это определённый объект, вычисляемое поле или материализованный документ, необходимый для работы; не требуется строить все возможные объекты без необходимости.
2. **Проверяю доступность источников.** Данные, схемы и объявленные зависимости должны быть доступны; при недоступных входах понятно, что результат сейчас получить нельзя.
3. **Получаю результат сборки.** Движок читает источники, выполняет необходимые builders и формирует собранный объект. Пользователь получает первую пользу, когда пригодное значение стало доступно, а не только после появления Markdown.
4. **При необходимости получаю Markdown.** Если нужен текстовый документ, движок использует renderer. Если нужен структурированный объект для Workspace, обязательной генерации и обратного парсинга Markdown нет; конкретная доставка объекта UI ещё открыта.
5. **Учитываю изменения.** При изменении исходных данных/проектного кода выясняю, что необходимо пересобрать. Автоматически вычисляемые зависимости не делают семантические суждения достоверными без соответствующего ревью.
6. **Использую результат.** Объект/представление доступен для чтения или [визуализации](WORKSPACE_VISUALIZATION_CANDIDATE.md), а источник и статус понятны. Обновлённые значения дают повторную пользу.

**Альтернативы и восстановление:** если вход отсутствует, идентификатор неверен или builder завершился ошибкой, результат не выдаётся за успешный; если объект устарел — требуется пересборка или явная отметка состояния; если semantic review не выполнен — вычислительная сборка не изображает смысловую проверку. Готовый previously materialized документ может быть читаем, но его актуальность нельзя подразумевать.

**Реальные costs:** ввод/изменение структурированных полей, написание и сопровождение builders, проверка/ожидание сборки, вычислительные ресурсы, доверие к проектному коду и человеческое ревью. Численные задержки, суммы, частота пересборки и способ исполнения неизвестны. Сроки разработки bridge Gendocen→UI — отдельный реализационный слой.

**Примечание о границе сценариев:** этот путь оправдан, только когда пользовательская задача действительно включает получение вычисленного объекта или обновление представления; сам технологический вызов builder не создаёт самостоятельной новой глобальной User Need или FR.
